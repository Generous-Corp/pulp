## What changed

The format adapters no longer install pulp-content's preset source on the
`PresetManager` they own. It never had an effect: no adapter sets a content
plugin id, so `content_presets()` was always empty. With it gone, no format
target links `Pulp::content`, so these targets no longer bring it onto a
consumer's link line:

- `Pulp::format`, `Pulp::format-core`, `Pulp::format-view` and `Pulp::format-clap-core`
- `Pulp::host`, `Pulp::standalone`, `Pulp::standalone-native` and `Pulp::sequence`
- `Pulp::dsl`, `Pulp::view-graph-editor` and the `Pulp::inspect-*-runtime` targets

`parse_content_capability_manifest`, `load_content_capability_manifest` and
`content_capability_manifest_to_json` moved from `Pulp::content` to
`Pulp::state`. They are declared in
`<pulp/state/content_capability_manifest.hpp>`, which
`<pulp/state/content_registry.hpp>` still includes. `Pulp::content` now links
`Pulp::state`.

## Who is affected

- Code that calls `ContentRegistry`, `content_registry_preset_source()`, or the
  content-pack install and preview API while linking only one of the targets
  above. It previously linked by accident through the format adapters, and now
  fails with undefined `pulp::state::ContentRegistry` symbols.
- Plug-ins and applications that do not use the content registry: no change.
- Code that only parses or writes a plugin runtime manifest can now link
  `Pulp::state` alone.

## Migration steps

Link `Pulp::content` explicitly wherever you use the registry:

```cmake
target_link_libraries(my_target PRIVATE Pulp::format Pulp::content)
```

For a target made by `pulp_add_plugin`, link the per-format targets, for
example `MyPlugin_VST3` and `MyPlugin_CLAP`, as
`examples/moonbase-activation/CMakeLists.txt` does.
