## What changed

A gradient whose last stop is fully transparent — `rgba(0,0,0,0)`, the usual
way to write a wash, scrim, vignette or fade — now keeps its colour as the
alpha falls instead of sliding toward black. The result is brighter and more
saturated across the ramp, and it is what CSS specifies.

Nothing about the API moved. The same `set_background_gradient_linear` /
`set_background_gradient_radial` call with the same stops produces different
pixels.

**Only gradients with a transparent stop are affected.** A ramp between two
opaque colours is byte-identical across this hop.

## Why you may not notice, and why your tests will

The shift is invisible at a glance and large in a digest. Measured on a
1280x800 frame carrying two `rgba(...,0x1A)`-to-transparent radial washes: the
maximum per-channel change is **7 of 255**, spread over 53% of the pixels. No
reviewer spotted it by eye. Every pixel-exact baseline over that frame went red
at once.

If you keep golden images or digest comparisons of any surface with a
fade-to-transparent gradient, expect them to fail across this hop, and expect
the failure to look like a regression in your own code.

## What to do

1. **Look at the diff before you re-record.** A stale baseline and a real
   regression fail identically. Amplify the difference (`ImageChops.difference`
   times ~12) and confirm the change is confined to gradient areas and that
   glyphs, borders and solid fills are untouched.
2. **Prove it is the toolchain, not you.** Build the same source against your
   previous SDK prefix and re-run:

   ```
   cmake -S . -B build-old -DCMAKE_BUILD_TYPE=Release \
     -DCMAKE_PREFIX_PATH=/path/to/previous/sdk
   cmake --build build-old --target <your-render-test> -j4
   ```

   Green on the old prefix and red on the new one means the images are stale.
3. **Re-record, and record what recorded them.** Store the SDK version beside
   the baselines so the next hop can tell drift from a defect without repeating
   this investigation.

## Deciding which output is correct

Compute the expected value directly rather than trusting either render. For a
stop `C` at alpha `a0` fading to transparent over background `B`, premultiplied
interpolation — what CSS requires — gives, at fraction `t` along the ramp:

```
a = a0 * (1 - t)
result = B + (C - B) * a          # hue held, alpha falls
```

Unpremultiplied interpolation instead drags the colour toward black and yields
a visibly darker, greyer ramp. Sampling a controlled `rgb(94,120,255)` to
`rgba(0,0,0,0)` linear ramp over `#161A21` at the midpoint: the expected value
is `(58,73,144)`; ≤0.769.1 produced `(39,45,87)`, ≥0.773.1 produces
`(62,75,151)`. **The newer output is the correct one.** The same probe over an
opaque-to-opaque ramp matches exactly on both, which is how you know the change
is specific to the transparent stop and not a general colour shift.

## Where the change lives

Not in Pulp's gradient code. `core/view/src/view_paint.cpp` and
`core/canvas/src/skia_canvas_gradients.cpp` are unchanged for linear and radial
across this range — only the conic/sweep path moved. Pulp hands Skia
unpremultiplied `SkColor4f` stops and a default `SkGradient::Interpolation{}`,
so the premultiplied-or-not decision is Skia's, and it is the **bundled Skia
that differs**: the `libskia.a` in the two SDK prefixes differs in size and
sha256, and the header layout under `external/skia-build/` differs too.

The exact upstream revision could not be named, because the newer prefix's
`external/skia-build/` ships **no `VERSION.md`** — the older one records
`chrome/m151`, downloaded 2026-07-07, and the newer records nothing. A Skia
archive without provenance makes a rendering change like this untraceable after
the fact; restoring that file is worth doing before the next bump.
