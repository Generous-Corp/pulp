## What changed

- `FastMath::tanh(x)` was the [7/6] Lambert Padé with its output saturated to
  exactly ±1 for |x| > 4. That left a 6.7e-4 step at |x| = 4. It is now an
  odd [5/4] rational: the minimax fit of tanh in absolute error on [0, 5.24],
  constrained so that its value reaches 1 at 5.24. Its argument is clamped to
  ±`FastMath::kTanhClamp` (5.24).
  - The curve is continuous and bounded.
  - Its numerator is scaled by 1 − 2⁻²¹, so results stay strictly inside ±1.
    Beyond the clamp the result is about ±0.9999996, not ±1.
  - The slope at the origin is 0.99976, not 1.
  - Because the error is now equiripple, results anywhere in (-5.24, 5.24)
    can move by up to about 5.7e-5 relative to before. Between 4 and 5.24
    they move by up to about 6.7e-4, toward `std::tanh`.
  - A NaN input still returns NaN.
  - It costs about 30% less per element than before: nine operations and a
    division, the same count as the unclamped Padé.
- `LadderSaturation::realtime_efficient` now evaluates the new
  `FastMath::tanh_minimax_recursive()`. That covers
  `LadderFilter::process_realtime_efficient()` and the tom voice's
  `realtime_efficient` noise ladder. It uses the same fit, clamp and bound as
  `FastMath::tanh_minimax()`, in Estrin form. Its results differ from before
  by a few float ulps. It removes a 2.6x slowdown of this profile inside
  polyphonic voice loops.

## Measured error

Worst absolute error against double `std::tanh`, over every finite float:

| Function | With fused multiply-add | Without (GCC, MSVC, x86-64 without FMA) | Largest result |
|---|---|---|---|
| `FastMath::tanh`, before | 6.71e-4 | 6.71e-4 | exactly 1 |
| `FastMath::tanh`, now | 5.69e-5 | 5.69e-5 | 0.99999964 (FMA), 0.99999958 (no FMA) |
| `FastMath::tanh_minimax` (unchanged) | 3.70e-6 | 3.72e-6 | exactly 1 |
| `FastMath::tanh_minimax_recursive` (new) | 3.67e-6 | 3.70e-6 | exactly 1 |

All four functions are odd.

## Migration steps

- Code that compared `FastMath::tanh(x)` to exactly ±1 for large |x| should
  compare against `FastMath::tanh(FastMath::kTanhClamp)`.
- Code that relied on `FastMath::tanh` matching the Lambert Padé below
  |x| = 4 should evaluate that fraction itself.
- No change is needed for `tanh_minimax()`, `tanh_accurate()` or the default
  ladder saturator.

## What changed

On macOS, `pulp_add_plugin()` now builds a plug-in's VST3, CLAP, AU v2 and
Standalone binaries with the lite editor stack unless the plug-in declares
`UI_SCRIPT`, `GPU_UI` or `FULL_EDITOR`. The lite stack leaves out the GPU
plug-in and window hosts and links lite replacements for the library
functions that reached Skia unconditionally, so the VST3, CLAP and AU v2
modules carry no Skia, Dawn or Tint. An AutoUi plug-in module drops from about
19 MB to about 2.1 MB stripped per format, and its first load in a host gets
faster in proportion. The Standalone app opens the same lite editor but still
links Dawn through the standalone host's own render code.

Editors that already opened on the CoreGraphics host (Pulp's generated AutoUi
editor, and C++ views that never set `requires_gpu_host()`) render the same.
That host paints text through CoreText; the lite stack also measures through
CoreText, and it answers `resolved_face_identity()` with the face CoreText
paints, so a design-imported panel still reuses the line breaks its capture
recorded. Measured against the full stack: PulpGain, Pulp Delay and
PulpDesignSynth are pixel-identical. PulpDesignArp differs in one 9 px label,
a bold "07", whose glyphs are identical but sit 0.5 logical px lower in lite.

That label and any text like it can differ by up to 1 logical pixel, because
the face it asks for is not one Pulp bundles, and Skia and CoreText fall back
to different faces for it. The capture resolved "JetBrains Mono" at weight 700
to JetBrainsMono-Bold. Pulp bundles only JetBrains Mono Regular. Skia skips the
Regular face for a bold request and falls through the stack to Menlo-Bold
(ascent 9.47, descent 3.55, leading 0.12 at 9 px); CoreText resolves the
bundled JetBrains Mono (ascent 10.08, descent 3.60, no leading). The
CoreGraphics host paints with CoreText in both builds, so the full build places
JetBrains Mono glyphs using Menlo-Bold's metrics, while lite measures the face
it paints. Advances agree (5.40 px per digit in both), so widths and line
breaks do not change, only the baseline. Neither stack's face matches the
capture's JetBrainsMono-Bold, so neither reuses that label's captured breaks.
The same holds for system families at non-400 weights ("Helvetica Neue" 600 at
12 px: ascent 13.92 and width 116.7 in Skia, 13.69 and 120.0 for the painted
face). To get identical placement in both builds, bundle or register
(`register_font`) the exact faces a design uses.

Two kinds of plug-in need the full stack and must now say so:

- A scripted UI (`UI_SCRIPT`) keeps the full stack automatically.
- A C++ editor with a view that returns `requires_gpu_host()` true needs
  `GPU_UI`. Without it, the editor logs

  ```
  [plugin-gpu-host] this editor asked for the GPU host, but the plug-in was built with the lite editor stack ...
  ```

  once and opens on the CoreGraphics host, where GPU-only drawing (Skia SVG,
  shaders, Dawn textures, 3D) is blank.

`FULL_EDITOR` links the full stack for any other reason. Other platforms are
unchanged: they always build the full stack.

## Migration steps

1. Search your plug-in's editor code for `set_requires_gpu_host(true)` or an
   override that returns true. If you find one, add `GPU_UI` to that
   plug-in's `pulp_add_plugin(...)` call.
2. If the editor draws through Skia-only APIs on purpose (custom
   `SkiaCanvas` code, `draw_svg` that must composite, GPU shaders) without
   setting the flag, add `GPU_UI` and set the flag on the editor's root view
   so the host is chosen correctly.
3. If you need the full stack for another reason, add `FULL_EDITOR`.
4. Rebuild and open the editor once. A `[plugin-gpu-host] ... lite editor
   stack` line in the log means a view still asks for the GPU host; declare
   `GPU_UI` for that plug-in.
5. `LITE_EDITOR` on its own still works and states the default. If a plug-in
   that declares it also gets `GPU_UI` or `FULL_EDITOR`, remove `LITE_EDITOR`:
   the combination is a configure error.

## Breaking changes

- `OnlineActivation::activate`, `deactivate` and `check_status` refuse a
  `server_url` that is not `https://`. A plain-http URL fails before any
  request is sent (`activate` returns nothing, `deactivate` returns false,
  `check_status` returns `LicenseStatus::NotFound`). The new
  `OnlineActivationOptions::allow_insecure_http` re-admits `http://` for a
  loopback test server.
- `check_status` sends `POST /status` with the JSON body
  `{"key":"...","machine":"..."}` instead of `GET /status?key=...&machine=...`.
  A license server that only handles the GET form stops answering.
- The `/status` response is parsed, not searched: it must be a JSON object
  whose `status` member is exactly `"valid"` or `"expired"`. A body such as
  `{"valid":true}` or any other text containing the word is
  `LicenseStatus::InvalidSignature`.
- Every request field (serial, product id, license key, machine id) is
  JSON-escaped. A serial containing `"` or `\` arrives intact instead of
  corrupting or extending the object.

## Migration steps

- Point clients at an `https://` origin. For a local test server pass
  `OnlineActivationOptions{.allow_insecure_http = true}` as the trailing
  argument.
- On the server, accept `POST /status` with a JSON body and reply with
  `{"status":"valid"}` or `{"status":"expired"}`; any other value denies.
- Servers that already escaped incoming JSON need no change; servers that
  pattern-matched the raw body should parse it.

## Breaking changes

- `pulp::osc::Receiver::listen` and `listen_with_options` bind `127.0.0.1`
  instead of every interface. A receiver that previously accepted packets from
  a hardware controller or another machine on the LAN now only hears the local
  machine until it opts in.
- `ReceiverOptions::bind_address` is new. It takes an IPv4 literal; hostnames
  and IPv6 literals make `listen` fail instead of being resolved.
- `Receiver::local_address()` is new and reports the address actually bound.

## Migration steps

- To keep LAN reachability, switch the call to `listen_with_options` and set
  `options.bind_address = std::string(pulp::osc::kBindAllInterfaces);`
  (`"0.0.0.0"`). Nothing else in the options changes.
- To restrict a receiver to one interface, pass that interface's IPv4 address
  as the literal.
- Code that only ever sent to `127.0.0.1` needs no change.

## What changed

Both qualities of the `polyphase_iir` lane (the default oversampler) use
elliptic half-band designs with a narrower transition. The passband edge moves
to 0.485 of the base rate and the stopband starts at 0.515, so harmonics a
callback creates just above base Nyquist now meet the full stopband instead of
the transition band. `Quality::standard` uses twelve sections at stage 0
instead of six; `Quality::pristine` uses sixteen instead of eleven.

| | Before | After |
|---|---|---|
| Standard rejection | 94.8 dB from 0.58 Fs | 114.6 dB from 0.515 Fs |
| Pristine rejection | 146.3 dB from 0.55 Fs | 153.2 dB from 0.515 Fs |
| Passband, standard / pristine | flat (< 1e-8 dB) to 0.42 / 0.45 Fs | flat (< 1e-8 dB) to 0.485 Fs |
| Standard delay near DC, x2 / x4 | 2.66 / 3.49 base samples | 3.79 / 4.90 base samples |
| Standard delay at 0.4 Fs, x2 / x4 | 7.6 / 8.6 base samples | 12.6 / 13.9 base samples |
| Pristine delay near DC, x2 / x4 | 4.56 / 5.98 base samples | 5.16 / 6.87 base samples |
| Round-trip cost with a tanh callback, standard x2 / x4 | 1 | about 1.10 / 1.05 |
| Round-trip cost with a tanh callback, pristine x2 / x4 | 1 | about 1.06 / 1.09 |

A tanh driven at 5 kHz into a 48 kHz base rate puts its fifth harmonic at
0.521 Fs. Before, that harmonic sat in the transition band and aliased at
-45.5 dBc (standard) and -70.5 dBc (pristine) at x2 and x4 alike. Now the
x4 round trip aliases at -147 dBc (standard) and -167 dBc (pristine). At x2
both read -91 dBc, which is the fold the callback creates above the
oversampled Nyquist before any filter sees it.

The float build's stages also keep their state in double now, so a float
round trip adds only the rounding of its float samples (about -150 dB)
instead of -132 to -139 dB of accumulated section rounding.

The delay remains uncompensated: `latency()` still reports a non-constant
delay and `latency_samples()` still returns 0.

## Who is affected

Code that uses the default kind or selects `polyphase_iir`. Aliasing drops
and the top of the band is flat further up; the extra delay matters only where
the oversampled path is mixed with or aligned against another signal.

## Migration steps

Nothing is required. To align a dry path, read the delay from the filter
rather than hard-coding it:

```cpp
const double delay = oversampler.group_delay_samples(0.0); // base samples
```

For a constant, host-compensated latency use `Kind::linear_phase_fir`.
Filter figures for every kind are in
[Oversampling filters and the real-input FFT](../reference/oversampling-and-real-fft.md).

## What changed

The code that builds a scripted editor from declared editor assets now links only
into binaries that ask for it. A target that declares `UI_SCRIPT` (or gets a
script from `pulp_use_kit_ui()`) asks automatically through its generated
editor-assets source, so nothing changes for it. Plug-ins whose editor is
AutoUi no longer link the script runtime, which takes about 5 MB out of each
stripped module.

A multi-plug-in bundle whose scripts come only from hand-written
`PluginRegistration::ui_script` entries, with no `UI_SCRIPT` on any of its
targets, does not ask. Its editors now open AutoUi and log:

```
Scripted editor UI '<path>' not built: this binary declares a scripted editor but does not link the script runtime; ...
```

`ViewBridge::last_error()` carries the same reason.

## Migration steps

1. Call the installer once in that bundle, for example next to the
   `register_plugin()` calls:

   ```cpp
   pulp::format::install_scripted_editor_builder();
   ```

   Or declare `UI_SCRIPT` on one of the bundle's format targets.
2. Open an editor and confirm the log line above is gone.

## What changed

On macOS, `pulp ship package` used to exit 0 even when it built nothing.
It printed `FAILED to create combined installer` (or `FAILED` for a
per-format `.pkg` or `.dmg`) and `Created 0 .pkg and 0 .dmg artifacts`, and
returned success. It now exits 1 in two cases:

- any installer failed to build. Each failure still prints its `FAILED`
  line, followed by `Error: N installer(s) failed to build`.
- nothing was packaged, because no plugin bundles or standalone apps were
  found under `build/`. The message is `Error: nothing to package`.

A run that builds every installer it attempts still exits 0. The Linux
packager already exited 1 when it found no plugins; macOS now matches it.

`pulp ship release` stops at its package stage in these cases instead of
going on to notarize. Before, it reached notarization with nothing to submit.

## Who needs to act

Only scripts that call `pulp ship package` and expect exit 0 from a run
that produced no installer. Those scripts were treating a failure as
success. Check that `build/` holds the bundles you mean to ship, or that
the installer identity exists in the signing keychain (`pulp ship doctor`),
before calling `package`.

`pulp ship` also now works in an SDK consumer project (`pulp.toml`, no
`core/`). It used to stop there with `not in a Pulp project directory`. No
action is needed for that.
