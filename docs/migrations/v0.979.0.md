## What changed

`<pulp/view/widgets.hpp>` and `<pulp/view/view_all.hpp>` no longer include
`<pulp/view/audio_bridge.hpp>`. `AudioBridge` and the other audio-side view
types are provided by `pulp::view-audio`, whose headers live under
`core/view/audio/include`. That target's `<pulp/view/audio_widgets.hpp>`
includes `audio_bridge.hpp`, and `widgets.hpp` reaches `audio_widgets.hpp` only
when `pulp::view-audio` is linked (it publishes `PULP_VIEW_HAS_AUDIO_WIDGETS`).

## Who is affected

Code that named `pulp::view::AudioBridge` (or another declaration from
`audio_bridge.hpp`) while including only `widgets.hpp` or `view_all.hpp`, and
that links only `pulp::view-core`, `pulp::view-script` or the view-platform
composition, now fails to compile with an unknown-type error for `AudioBridge`.

Consumers that link `pulp::view`, `pulp::view-native`, `pulp::view-audio`, or
use `pulp_add_plugin` / the standalone host are not affected: those link
`pulp::view-audio`, so `widgets.hpp` still reaches the audio declarations.

## What you need to do

- Include `<pulp/view/audio_bridge.hpp>` directly wherever `AudioBridge` is
  used, rather than relying on `widgets.hpp` or `view_all.hpp`.
- Link `pulp::view-audio` (CMake `target_link_libraries(<target> PRIVATE
  pulp::view-audio)`, or `Pulp::view-audio` from an installed SDK). It brings
  the `core/view/audio/include` directory and the audio, signal and MIDI
  libraries `AudioBridge` depends on.
- Code that needs no audio types can keep linking `pulp::view-core` alone; it
  should not name `AudioBridge` at all.
