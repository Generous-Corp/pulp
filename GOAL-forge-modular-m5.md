# GOAL — Forge Modular working end to end on the M5

Hand this back to start the work. The plan and the current state live in

## The goal

Deliver Forge Modular to the M5 as **all four formats** — AU, VST3, CLAP and the
standalone app — with VCV Rack creation working from every one of them:

- Type a prompt, get a working Rack **module**: it compiles, passes the behaviour
  gate, installs into Rack, loads there, and its knobs move and do something.
- Switch to Patch, type a prompt, get a working Rack **patch**: it loads in Rack,
  **makes sound**, and explains itself at Terse / Standard / Learning depth.
- Both open in Rack from the app.
- The machine is set up by running one script. Nothing is hand-carried.

Do not stop and ask what to do next. Work the plan. If a step is blocked, finish
every step that is not, and say plainly which one is blocked and why.

## The bar — what "ready" means

**Do not tell me it is ready until you have personally verified all three of
these, on the M5, on the binaries that will actually be there:**

1. **CLI.** A module and a patch each generated from the installed toolchain,
   with the log showing gate passed and installed.
2. **The standalone app.** A module and a patch each generated by *clicking
   Build* — not from a terminal. The status card tracks the run; the chat stays
   quiet apart from the verdict.
3. **REAPER.** The CLAP, AU and VST3 each loaded in REAPER, editor open, and a
   module generated from inside the DAW.

"It should work because it shares the seam" is not verification. Neither is a
green test suite. Run it.

If a check fails, that is a finding, not a delay — report it with the evidence
and keep going on everything else.

## What proof to bring back

For each of the three surfaces, the thing itself rather than a description:

- the generator log's last lines (`gate passed`, `installed →`)
- Rack's own log naming the plugin, and a capture of the module or patch in Rack
- for a patch, the measured audio from the patch gate (mean and peak volts)
- for REAPER, the smoke's verdict line per format
- `auval` / `clap-validator` / VST3 load-probe results **from the shipped
  binaries**, re-run after signing

State anything you could not verify and why. A skipped check reported as skipped
is fine; a skipped check reported as a pass is not.

## Standing constraints

- Work in `/Volumes/Workshop/Code/pulp-modular-rack`, branch `explore/modular-rack`.
  Nothing goes to `main` without being asked.
- Nothing Rack-shaped leaks into Forge Instrument / MIDI / FX. The no-leak guard

- Launching Rack, REAPER or the standalone opens an audio device: say so before
  you do it, cap the run, and quit gracefully. Never hard-kill Rack — it
  truncates the log and triggers crash recovery.
- Do not install anything on the M5 until the work is ready for me to test.

## A note on how to spend the time

The CLI is the cheap loop and everything about generation quality is debuggable
there in one command. The app and REAPER prove wiring — necessary, but slow and
focus-sensitive. Use the cheap loop to find defects and the expensive ones to
confirm the paths, not the other way round.

Seven of the defects fixed so far were the same shape: the model being judged by
a rule it was never told, or shown a vocabulary that hid what it needed. When a
generation fails, check what the model was actually given before assuming it
chose badly. And when a knob is reported inert, check the probe before blaming
the module — the gate's CV stimulus was a constant, which made every slew and
glide control look dead while working perfectly.
